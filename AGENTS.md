# Working notes for agents

## The command system was replaced with Brigadier, and every command deleted

**This landed as a feature during the bug-fixing phase below, at the user's explicit call**,
and it is the one thing on this page that is not a bug fix. Read it before touching anything
that runs or tests a command.

The old framework was an unfinished leftover: one abstract `Command`, a static `Command[256]`
with a static cursor, `holder.command.split(" ")`, and arity dispatch (`args.length == 4/3/2`)
that made `/tp Alice 1 2` parse as coordinates. Tab completion read a second, hand-written
`suggestions()` table that the parser never consulted, so the two disagreed. Non-`CommandException`
throwables — commonly an out-of-bounds `args[n]` — were logged at WARNING and the sender was
told nothing at all.

It now runs on `com.mojang:brigadier:1.3.10`. See DEVELOPING.md for the shape and for how a
command is registered. What matters here:

- **The dispatcher ships nearly empty.** All 64 commands were deleted, not translated — the
  user's call, on the grounds that the set was bloat. `CoreCommands`/`ClientCommands`/`ServerCommands`
  are the three registration hooks. Commands come back one at a time, and **`/give` is the first
  one back** (`commands/core/GiveCommand.java`, op-only, both sides). It takes the two forms the
  user asked for — `/give <item id>` and `/give <player> <item id>` — and no count argument, so
  it is *not* a drop-in for the twelve dead smoke suites below, which all called `/give <id> <count>`.
  It hands over one full stack. Read the DEVELOPING.md note on sibling argument branches before
  adding a second command shaped like it: registration order decides which form wins, and a
  branch that throws loses its error message to whichever sibling parsed.
- **Twelve smoke suites are dead as a result**, and this is known and accepted. The rig drove
  the server with `setblock` (27 uses), `teleport` (15), `weather` (8), `give` (8), `clearinv`
  (8), `gamerule` (6), `effect` (5), `time`/`summon`/`count` (3 each) and `kill`. `:server:smokeTest`
  cannot pass until this is dealt with. **The agreed follow-up is to give `Bot` direct
  server-side helpers** (`setBlock`, `giveItem`, …) so the rig stops depending on the command
  surface at all, rather than to bring those twelve commands back to serve it.
- **`/stop` is back** (`net.minecraft.server.commands.StopCommand`, op-only, dedicated server), initiating a graceful server shutdown.
- **`/kick <player>` is back** (`net.minecraft.server.commands.KickCommand`, op-only, dedicated server).
  It lives in `ServerCommands` rather than `CoreCommands` because `ConfigManagerClient.kickPlayer`
  is an empty method — registered in core it would be a command that silently does nothing in
  singleplayer. It answers the sender *before* it kicks, so kicking yourself still confirms.
  Covered by `KickSmokeTest` (needs `kickbot` in `run/server/ops.txt`).
- **`/ban <player> [reason]` and `/unban <player>` are back** (`BanCommand`, `UnbanCommand`,
  op-only, dedicated server). **Nothing new was written to make them work** — `BanList`,
  `BanEntry`, `banned-players.txt` and the login refusal in `ServerConfigurationManager.login`
  were all still there, unreferenced by any command since the purge; these two are a front end
  onto `ConfigManager.banPlayer`/`pardonPlayer`. `/ban` takes a name, not an online player, so
  an absent player can be banned; if they *are* online it kicks them with the same wording the
  login refusal uses. The reason is a greedy trailing string and is optional; omitted, `BanEntry`
  supplies its own default ("Banned by an operator."). `BanEntry` also carries a `banEndDate`
  that nothing sets — **temporary bans are already modelled and already expire** (`removeExpiredBans`
  runs on every `isBanned`), so a `/tempban` would need a date parser and nothing else.
  `/unban` reads `getBannedPlayers().isBanned` (a `ServerConfigurationManager` cast —
  `ConfigManager` does not expose it) so a typo comes back as "That player is not banned."
  rather than silently doing nothing. Covered by `BanSmokeTest` (needs `banbot` in
  `run/server/ops.txt`); it always pardons what it banned, and proves the pardon by logging
  back in. **Together, /kick /ban /unban moved `HelpSmokeTest`'s hardcoded op command list from
  three entries to six.**
- **`/tp <x> <y> <z>` is back** (`commands/core/TpCommand.java`, op-only, both sides — the
  client implements `teleportPlayerTo` for real, so unlike `/kick` it belongs in `CoreCommands`).
  **Nothing new was written for the coordinate parser either**: `Vec3Argument`, `WorldCoordinate`
  and `WorldCoordinates` already parsed `10 20 30`, `~ ~5 ~` and `~-2.5 ~ ~1.25`, and had no
  caller outside `CommandFrameworkSmokeTest`'s scratch tree. It teleports the sender, and the
  sender of a command block's line is the nearest player within 16 blocks — so `/tp ~ ~ ~` in a
  command block yanks that player onto the block (`~` is the block, the mover is the player),
  and with nobody in range it is "That command has to be run by a player." That source carries a
  null `ConfigManager` (nothing in `:core` can hand it one), so `/tp` moves the entity directly
  there rather than through `teleportPlayerTo` — right in singleplayer, but on a dedicated server
  the client is never told and the next movement packet rubber-bands the player back, so it does
  nothing. None of this is exercised: the command block path has no coverage at all.
  One thing did change under it: `CommandSourceStack.of` now stores `posY - yOffset`, so `~`
  resolves against the feet — see the DEVELOPING.md note. That is a no-op on the dedicated
  server (`EntityPlayerMP` zeroes `yOffset`) and therefore **not something `TpSmokeTest` can
  catch**; it is singleplayer, where `LocalPlayer` keeps 1.62, that `/tp ~ ~ ~` would have
  walked up. Covered by `TpSmokeTest` (needs `tpbot` in `run/server/ops.txt`), which never
  calls `sink()` — a bot that holds still is a bot the server counts as floating, and 80 ticks
  of that is a kick, so it spends the counter with a short `settle()` and re-anchors between
  phases. The op list in `HelpSmokeTest` is now **seven**.
- **`/op <player>` and `/deop <player>` are back** (`OpCommand`, `DeopCommand`, op-only,
  dedicated server — `ConfigManagerClient.opPlayer`/`deopPlayer` are empty, so `CoreCommands`
  would make them silent no-ops in singleplayer). **Nothing new was written here either**:
  `ServerConfigurationManager.opPlayer`/`deopPlayer` already maintained the `ops` set, rewrote
  `ops.txt` and broadcast an `OpPacket`; `ConfigManager` already exposed `isOp`, so unlike
  `/unban` neither of these needs a cast. Both take a name rather than an online player, so an
  absent one can be opped, and both refuse a no-op ("That player is already an operator." /
  "That player is not an operator.") rather than doing nothing to a typo.
  What makes the grant live is `NetServerHandler.createCommandSource` asking `isOp` on **every**
  command, so a player opped mid-session is opped for their next line without relogging — that,
  in both directions, is what `OpSmokeTest` actually checks (needs `opbot` in `run/server/ops.txt`
  and needs `sidekick` to stay out of it; it always deops what it opped). Note that `saveOps`
  rewrites the file from a `HashSet`, so **every /op or /deop reshuffles the order of ops.txt**
  and drops any comment or blank line in it. The op list in `HelpSmokeTest` is now **nine**.
- **`/gamemode <mode> [player]` is back** (`commands/core/GamemodeCommand.java`, op-only, both
  sides). `GamemodeArgument` takes a name, an initial or `0..3`. The command is four lines; what it
  needed underneath is the section below. The op list in `HelpSmokeTest` is now **ten**.
- **`/score add|remove|set <player> <amount>` is back** (`commands/core/ScoreCommand.java`,
  op-only, both sides). **Nothing new was written to carry the value to the client**: the diff in
  `EntityPlayerMP.onUpdateEntity` (`score` against `lastScore`, sent as a `ScorePacket`) and the
  `ScorePacket` handler on the client were both already there, so writing `Player.score` is the
  whole command — in singleplayer it runs on the player itself. The catch that costs a debugging
  session is that `onUpdateEntity` is driven by `NetServerHandler`'s **movement** handling, not
  by the tick loop: a player whose movement packets the server is ignoring never learns their
  score changed. `remove` floors at zero rather than going negative, and the amount takes a new
  `NonNegativeIntArgument`, so `-5` comes back as "Amount must be 0 or greater" rather than
  parsing as an `add` in disguise. All three subcommands require an explicit player; there is no
  self form. Covered by
  `ScoreSmokeTest` (needs `scorebot` in `run/server/ops.txt` and needs `sidekick` to stay out of
  it). The op list in `HelpSmokeTest` is now **eleven**.
- **Command blocks stayed.** The block, the tile entity, its NBT and the edit screen are all
  untouched; `CommandBlock.onTick` runs its line through `Commands.active()` with a source
  anchored at the block, so `~` means the block rather than whoever is standing nearby. What
  went was the `CommandsManagerCore` registry it carried (a fourth copy of every core command)
  and its ~150-line stub `ConfigManager`. The old `catch (Exception) {}` around the whole
  dispatch is gone too, so a command block now reports its errors to the nearest player unless
  `suppressOutput` is set. With nothing registered it has nothing to run yet.
- **There is no tab completion**, and it is not a thing to re-add casually — see DEVELOPING.md.
  The old one read the deleted `Command[256]` and a hand-written `suggestions()` table and went
  with them. `ChatScreen`'s Tab key now completes player names only.
- `PROTOCOL_VERSION` was **not** bumped. Nothing on the wire changed: commands still ride
  `ChatPacket`.
- Deleted with them: the whole `/worldedit` suite and `game.world.edit` (the selection was
  global statics, never per-player, so it was multiplayer-broken anyway), its `exporter`
  package, `CommandUseTimer` + the unregistered `CommandDevItems`, and 247 of the 253 keys in
  `commands.lang`. `DebugStick` was the WorldEdit wand and is now an inert position readout —
  **whether that item stays, changes or goes has not been decided.**
- `ConfigManager` moved out of `net.minecraft.commands` to `net.minecraft.game.player`. It is
  the server's player registry, not a command type; commands were only ever a caller.

Two things worth knowing because they were found rather than designed:

- **The stdin thread is running before `worlds` is populated.** Building the command source at
  queue time NPEs on a command typed during startup; it is built at drain time instead, which
  is why `addCommand` takes a `Supplier<CommandSourceStack>` rather than the source itself.
  Found by piping a command into the *shipped server jar*, not by any test.
- **Brigadier does not filter completions by `requires()`** — the trap waiting for whoever
  wires completion up later. Vanilla only appears to because it sends each client a
  pre-filtered command tree.

### Verifying command work

```bash
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.CommandFrameworkSmokeTest
                                            # the framework alone; no server needed
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.CommandWireSmokeTest
                                            # needs a running server; no op needed
```

`CommandFrameworkSmokeTest` still registers its own scratch tree, because `/give` alone is not
enough to exercise the framework. It covers dispatch, `requires()` gating, the error cursor, and relative coordinates.
`CommandWireSmokeTest` is the half it cannot reach: that a real `ChatPacket` beginning with `/`
still arrives at the dispatcher and gets an answer back.

```bash
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.GiveSmokeTest
                                            # needs a running server and "givebot" in ops.txt
```

`GiveSmokeTest` covers `/give` itself: both forms landing in a slot, and the three ways it can
be told no.

```bash
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.TpSmokeTest
                                            # needs a running server and "tpbot" in ops.txt
```

`TpSmokeTest` covers `/tp` and the `~` reader on the wire: absolute coordinates landing exactly,
offsets up, down and fractional, a bare `~ ~ ~` moving nothing, and the two ways a position can
be malformed.

```bash
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.OpSmokeTest
                                            # needs a running server, "opbot" in ops.txt,
                                            # and "sidekick" not in it
```

`OpSmokeTest` covers `/op` and `/deop`: both no-op refusals, the confirmation lines, and — the
half worth having — a second bot gaining and then losing op mid-session, proved by what it is
allowed to run rather than by the chat.

```bash
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.GamemodeSmokeTest
                                            # needs a running server and "modebot" in ops.txt
```

`GamemodeSmokeTest` covers `/gamemode` and the server behaviour behind it; see the gamemode section
for what it pins down and how it was measured red.

```bash
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.ScoreSmokeTest
                                            # needs a running server, "scorebot" in ops.txt,
                                            # and "sidekick" not in it
```

`ScoreSmokeTest` covers `/score` on the wire: the permission gate, the arithmetic including the
floor at zero, a named player's score reaching that player's own client, the sender's three
confirmation lines, and the four ways it can be told no. Two things about it are worth knowing
before editing it. It never calls `settle()`, because that helper sinks 0.2 before each send:
once the login corrective teleport clears `hasMoved`, the bot never re-echoes `lastPos` within
the 0.1 re-arm tolerance and the server silently ignores every packet it sends for the rest of
the run — no ticks, so no score sync, while chat replies keep arriving because `handleChat` is
ungated. And every expected value is relative to a score the test pins itself, because a set to
the score the player already has sends nothing (`score == lastScore`) and would make the packet
checks coin flips. All seven suites pass at HEAD.

**Neither covers the command block** — that path needs a real `World` with a redstone signal
and has not been exercised at all, by a bot or by hand.

## Gamemode is server-authoritative now, and the client controller is transport-only

Gamemode used to be a client-only idea. Nothing carried it on the wire, nothing on the server
acted on it, and `Minecraft.clientSetGamemode` was the only writer.

- **One source of truth**: `player.properties.gamemode`, saved as the NBT byte `Gamemode` in the
  player .dat and read by ~40 places in `:core` that run on both sides. `mc.gamemode` no longer
  answers "what mode am I"; it answers "do my interactions go over the wire", and there are two of
  them — `GameMode` (local) and `MultiplayerMode` (networked). `SurvivalMode`, `CreativeMode`,
  `AdventureMode` and `SpectatorMode` are **gone**; their behaviour moved into `GameMode`, branching
  on the mode. That collapse is the fix for the real bug: `MultiplayerMode extends SurvivalMode`, so
  all fourteen `instanceof CreativeMode` / `SpectatorMode` tests outside the package read as
  survival over the wire and creative, adventure and spectator did nothing in multiplayer. They are
  `properties` checks now, and `PlayerProperties` has `isCreative()` / `isAdventure()` /
  `isSpectator()` beside the raw int the old comparisons still use.
- **`GamemodePacket` (id 73, server→client)** carries it: at login from `NetLoginHandler.doLogin`
  after the NBT is read, from `recreatePlayerEntity` (respawn and dimension change are both that one
  method, and `Player.clone` already carries `properties` across), and on every `/gamemode`.
  Self-only — nothing consumes another player's mode; making spectators invisible to others would
  turn it into a broadcast.
- **`ConfigManager.setGamemode`** is the seam, exactly like `teleportPlayerTo`: the server sets and
  sends the packet, the client sets locally. That is why `/gamemode` can live in `CoreCommands` and
  still work in singleplayer.
- **The server enforces it now**, which it never did: no floating kick for creative or spectator
  (`NetServerHandler`), no rubber-band out of blocks for spectator, an instant break for creative in
  `ItemInWorldManager.useBlock`, and no drops and no tool damage for a creative break in `hitBlock`.
- **`CreativeSlotPacket` (id 107, client→server)** is how the creative inventory reaches the server:
  the client says "this stack is now in this slot", and the server applies it **only if it agrees
  the sender is in creative**, otherwise sending the real contents back. That gamemode check is the
  whole security of it — it is a client asking the server to conjure an item. What decides *when*
  to send one is a diff, not a click handler: `CreativeScreen` snapshots `player.container` and
  sends what changed on each update, the server's own detectAndSendChanges in reverse. Every route
  into that screen — mouse, shift, the drop key, the number keys, the bin — writes through the
  player container, and hooking them one at a time is how B-49 happened. Pick-block is the one
  creative write that happens with no screen open at all, so `GameMode.swapItem` sends its own
  (B-49b); anything else added later that moves items client-side in creative needs the same. `MultiplayerMode.windowClick`
  sends nothing at all when the open container is the creative one: it exists only on the client, so
  its slot numbers are meaningless on window 0 (B-20 records the same trap for the number keys).
- `ModeSwitcher` sends `/gamemode` in multiplayer rather than switching locally, so the server
  refuses a non-op; `NetworkWorld` no longer inherits the singleplayer `WorldSettings` statics.
  `DeathScreen`'s permadeath spectator switch is singleplayer-only — driving it server-side in
  multiplayer is **not done**.

`GamemodeSmokeTest` covers the server half (needs `modebot` in `run/server/ops.txt`): the packet at
login and on each form of the command, the mode surviving a relog, the floating kick exempting
creative and still catching survival, the instant break, no drops for it, and the creative slot
request being accepted in creative and refused in survival. **Measured red/green** — reverting the
`hitBlock` guard turns the drops check red, reverting the `useBlock` branch turns the instant-break
check red, and reverting the flight gate turns the creative-floating check red. The drops check only
means anything because the bot is holding a pickaxe: what stone drops is `canHarvestBlock`, so
bare-handed it is green against any build.

**The client half has no automated coverage and needs a human** — the mode collapse touches block
breaking, reach, flight, the HUD and the inventory screens. The client starts clean; nobody has yet
played creative, adventure or spectator in either world since.

## Current goal: bug-fixing phase

Multiplayer works end to end — login, chat, chunk streaming, movement, and all five dimensions
running server-side. What's left before new features is a backlog of real bugs found by playing.

**We are not starting Phase 4 (dimension transfer) until the board below is clear.** Layering
dimension transfer on top of unverified movement and sync would make transfer bugs nearly
impossible to diagnose.

### How a session works

**One bug per session.** Pick the top open bug, fix it, verify it, mark it done, stop. Don't
opportunistically fix three things — the point is that each fix gets a real verification pass
instead of a plausible-looking diff.

A session is done when:

1. The bug has a **named root cause**, not a symptom description. "The counter is only reset in
   the branch where it is never read" — not "players get kicked".
2. The fix is **verified against something that fails without it.** A log line from real play, a
   measurement, or a smoke test that goes red when reverted. Bot what is trivially bottable
   yourself; ask the user to play what is not — see "Bot it or play it" below.
3. `./gradlew build` is clean and `:server:smokeTest` passes.
4. The board below is updated with what was found, including anything ruled out.

Ruling a suspicion out is a real result. Record it.

suffix (`B-16b`) for a bug found while fixing another or regressed out of its fix.

## Authentication and distribution

`online-mode=true` works again. The old path called `session.minecraft.net`
(`joinserver.jsp` / `checkserver.jsp`), which Mojang decommissioned years ago, so every
online-mode login failed and the default was pinned to false. Both halves now speak the
modern endpoints: the client POSTs `sessionserver.mojang.com/session/minecraft/join`
(`ClientHandler.joinServer`) and the server confirms with `/hasJoined`
(`NetLoginHandler.hasJoined`). The access token never reaches the server — Mojang is the
middleman, which is the entire point of the three-way handshake.

Three things worth knowing before touching this:

- **No encryption handshake is involved, deliberately.** Mojang treats `serverId` as an
  opaque string and only checks that both sides sent the same one, so the existing random
  `Long.toHexString(rand.nextLong())` is enough. Vanilla 1.3+ derives that hash from a shared
  secret and the server's public key; skipping that means a hostile server could relay a
  join and impersonate the player elsewhere. Acceptable while we are the only server, and
  the reason not to advertise this as equivalent to vanilla's.
- **The token comes from the launcher, not from us.** Prism/MultiMC hand legacy instances
  their session as `token:<accessToken>:<uuid>`, which `Session` parses. There is no
  password login to fall back on — Yggdrasil was shut down in 2023 — so a client with no
  token cannot join an online-mode server at all. `Session.canAuthenticate()` gates that and
  produces a readable message instead of a mystery failure.
- **`online-mode` defaults to `true`**, so a server unpacked into a fresh directory is
  authenticated rather than wide open, and the first run writes the key into
  `server.properties` (nothing used to create that file at all). Dev needs the opposite:
  `Bot` throws the moment a handshake returns a real serverId, so an online-mode server makes
  the whole suite unrunnable. `:server:runServer` writes `online-mode=false` into
  `run/server/server.properties` when the key is absent, and never overrides an explicit one —
  if you set it to true by hand to play-test auth, the suite will fail until you set it back.

Identity is a bare username everywhere it matters (`ops.txt`, `white-list.txt`,
`world/players/<Name>.dat`), which is what makes offline mode dangerous on a reachable port
rather than merely unauthenticated: connecting as an opped name grants op, and connecting as
a name with a save file inherits that inventory. The whitelist is spoofable the same way and
is not a substitute.

**Distribution.** `:client:prismExport` builds a Prism/MultiMC instance export, the same
shape Infdev+ itself shipped as `Latest.zip`. The template lives in `dist/prism/`, extracted
from that original. The vanilla a1.0.4 jar is not in it and must not be added:
`patches/net.minecraft.json` points Prism at `launcher.mojang.com`, so the base game comes
from Mojang and the player supplies their own account. That is what keeps this a mod rather
than a redistribution of the game. `:server:serverJar` is the exception — it bundles the
whole game with no launcher in the loop, so it is for our own hosting, not for handing out.

### Probes and smoke tests

Two tiers. Most sessions only need the first.

**A probe** answers one question during diagnosis and is then thrown away. Drop a file with a
`main` into `server/src/smoketest/java/net/minecraft/smoketest/` and run it — `-PsmokeClass` takes
any main class, so nothing has to be registered anywhere:

```java
public class Probe {
    public static void main(String[] args) throws Exception {
        Bot bot = Bot.join(args, "probe");
        System.out.println(bot.await(EntityHealthPacket.class, 20000).food);
        bot.close();
    }
}
```

```bash
./gradlew :server:smokeTest -PsmokeClass=net.minecraft.smoketest.Probe
```

A probe that needs **no server at all** is the fastest signal there is: build a `World`, a `Chunk`
or an entity and read the answer off real game objects. That is what settled B-07 (`blocks[0] =
null`), B-12 (the box sinking 0.56 into the floor) and B-15 (the spawner's own geometry). Reach for
that before writing a bot.

**A smoke test** is a probe that earned a place in the suite: it demonstrated the bug on the wire
and you *watched it go red*. Promote it, delete the probe, add it to the list above. Never promote
a probe you have not seen fail — a check that has only ever been green proves nothing about the
game, only about itself.

`Bot` is the headless client — `join`, `read`, `await`, `awaitLast`, `awaitAll`, `drain`, `chat`,
`sendAction`, `sendState`, `settle`, `sink`, `followTeleport`, `positionOf`, `close`. `positionOf`
answers where this bot's client would *draw another entity*, accumulated from the same three packets
`ClientHandler` drives `Entity.serverX/Y/Z` from — it is how B-42 measured what an onlooker sees.
`Checks` is the tally —
`check`, `note`, `abort`, `done`. Three things they handle that cost real sessions to learn:

- **Every wait pumps every live bot.** The server ignores a player until its login teleport is
  echoed back exactly (`NetServerHandler.hasMoved`), so a bot that stops sending position packets
  is silently dropped and every assertion about it becomes meaningless — the `MovementSmokeTest`
  failure recorded in B-05. A watcher waiting on a mover keeps that mover alive with no
  interleaving by hand.
- **One bot per JVM if it decodes chunks.** `UpdateChunkPacket` and `UpdateSectionPacket` share a
  static scratch buffer. Bots trading small packets share a JVM safely; anything reading chunk data
  needs its own process (`TwoClientTest` spawns them).
- **A teleport switches the server off, and `followTeleport` switches it back on.** Every
  server-initiated teleport clears `hasMoved`, and `handlePlayerMovement` does *all* of its work
  inside one `if (hasMoved)` — movement, chunk streaming, the health sync. A bot that `/teleport`s
  and keeps sending its old position is not just ignored for movement: it stops receiving block
  updates for the chunk it is standing in, and its health never changes on the wire no matter what
  happens to it. `read()` now adopts every teleport as it arrives, the way a real client echoes one
  straight back, and `followTeleport` is how a test *waits* for a particular one. The catch is that
  an armed bot is also *eligible to be kicked*, so it needs to be standing on something — see below.

Three more things that cost this session real time, in the hope they cost the next one less:

- **A bot holding a position in mid-air is kicked as flying after 80 packets** — four seconds — and
  every assertion after that goes silently green because `read()` returns nothing. A *falling* bot
  is safe (`posY - d3 < -0.03125` resets the counter), and so is one in water, which is why
  `sink()` and `settle()` work at spawn. Standing still anywhere else needs a block under the feet:
  `DeathSmokeTest` `/setblock`s its own floor and teleports onto it at an integer Y.
- **Around the spawn, single block changes are invisible.** `ServerChunkDistance` sends one changed
  block as `UpdateBlockPacket`, 2–63 as `UpdateSectionPacket`, and 64+ as a whole-chunk resend — and
  the chunks near spawn churn hard enough to sit in that last case constantly (measured: 530
  `UpdateChunkPacket`s in six seconds). A test asserting on a specific block change needs a quiet
  chunk; the land at 875,150,768 is one, and a `/setblock` that comes back is the proof.
- **A bot that dies where the test builds leaves a block there.** `playerGrave` is block 282, it has
  no collision box, and nothing ever clears it — so the next run walks through it and cannot see it,
  but `BedItem` refuses to place into anything that is not air. B-42 lost a run to exactly that:
  two bots suffocated in bed, their graves landed in the *pillow* cells, and every later run failed
  as `no bed at 877,150,768 ... found block id 0`, naming the half that was fine. When a place stops
  working at a site that used to work, probe the block the item needs as well as the one you clicked.
- **`/setblock <x> <y> <z> 0` throws.** `BlockList.blocks[0]` is null (the B-07 finding), so air
  fails `checkBlockId` and the command errors — silently, from a bot's point of view. Reset a block
  by setting a *different real block*, not by clearing it. And a `setblock` that changes nothing
  sends nothing, which makes a re-run of the same test look like a missing packet.
- **The first `/teleport` into unexplored terrain stops the server dead for half a minute.** That
  region is generated synchronously on the main thread, and while it runs the server answers
  nothing at all — commands queue up unexecuted and every wait in the test expires in order, so
  the failure surfaces as whichever check happened to be waiting when the budget ran out rather
  than as a stall. Measured at 32 seconds for the land at 875,150,768 on a fresh world, against a
  10-second run once those chunks existed. Any teleport away from spawn wants a timeout in tens of
  seconds, not the 5–6 that is plenty everywhere else, and the first run of a new test against a
  new world is not evidence of anything until it has been run twice.
- **`settle()` does not arm `hasMoved`, and nothing warns you.** Anything measured through
  `onUpdateEntity` — the health sync, chunk streaming, and every per-tick effect on the player
  entity including `swingArms` — runs only inside `handlePlayerMovement`'s `if (hasMoved)`. A bot
  that just settles at the spawn used not to get there: the fall draws a corrective teleport, and
  `Bot.read` adopted only the **first** teleport it saw, so from then on the echo could never match
  (fixed in B-42 — it adopts every one now, which is what a real client does). B-32's
  first draft measured 80 consecutive movement packets with `hasMoved=false` and reported a bug
  that did not exist, with the fix already in. `followTeleport` after a real `/teleport` onto
  placed stone is what arms it — which means an op'd bot even when the test looks like it needs
  nothing. `CrawlSmokeTest` and `SprintSmokeTest` get away with `settle()` alone only because
  `handlePlayerState` and `handleEntityAction` are not gated on `hasMoved`.

Bots that `/give` themselves must be in `run/server/ops.txt`, with the server restarted after.

### Bot it or play it

**Write the bot when the question is trivially bottable. Ask for a play test when it is not.**

Trivially bottable — just do it, do not ask:

- a packet's contents, presence, absence or count on the wire
- the server's verdict on something a client sends: accepted, rejected, resynced, ignored
- slot arithmetic, ids, registries, save files, wire framing
- anything needing no server at all — a `World`, a `Chunk`, an entity, real game objects in a `main`

Needs a human — say so and stop:

- how something *feels*: knockback, animation timing, camera, sound, sluggishness
- anything needing real terrain under the player. The spawn is open ocean (B-01), so a bot cannot
  stand on land, dig a ceiling or crawl into a 1-block gap without op and a pile of setup
- the whole experience end to end — walk around for five minutes, report whether you get kicked

Ask in two or three lines: what to do, and what counts as pass or fail. Their answer is the
verification and it goes in the board's Verified column.

The cautionary tale is still worth knowing, because half of it is still live. `MovementSmokeTest`
(written for B-00a, deleted in B-05) reported "walked 15s clean" against a server that kicked every
real player within four seconds, for two reasons:

- **A bot can be moving and still be ignored.** `NetServerHandler.hasMoved` is cleared by every
  server-initiated teleport and re-armed only by an exact echo. **`Bot` handles this now** — it is
  why the harness exists.
- **It stood in the wrong place.** Open ocean, where `isInWater()` counts as support, so the check
  could never fire. **Nothing handles this for you.** A bot on the spawn point is in the sea.

The first hole is closed. The second is the one that decides which side of the line a bug falls on.
